# AWS 계정 빈틈 점검 서비스 설계 (가칭)

작성일 2026-10-28. 상태: 초안, 사용자 승인 전.

## 의도와 이유

수업 팀 프로젝트(3명, 개발은 사용자가 거의 전담, 발표는 12월 초)로 AWS를 활용한 서비스를 만든다. 사용자는 정보보안 전공이라 보안 주제를 원하고, AI를 활용해 보안 문제를 해결하는 방향을 선호한다.

컨셉: AWS 사용자가 자기 계정을 연결하면 설정상 빈틈을 찾아 주고, AI가 한국어로 "무엇이 왜 위험한지, 뭐부터 어떻게 고칠지"를 설명해 주는 웹 서비스.

왜 이 주제인가: 오픈소스 스캐너(Prowler)는 점검 항목 수백 개를 목록으로만 쏟아내서, 초보자는 뭐부터 고쳐야 할지 모른다. 이 간극을 AI 해설과 우선순위 정렬로 메운다. 스캐너를 직접 만들지 않으므로 개발 부담이 작고, 발표에서는 AWS 서비스 연계와 보안 설계에 집중할 수 있다.

## 목표

- 웹 화면(로그인, 계정 연결, 스캔 실행, 리포트 열람)을 제공한다.
- 연결한 AWS 계정을 읽기 전용으로 스캔하고, 결과를 위험도순으로 보여 준다.
- 각 발견 항목에 Gemini가 한국어 해설(위험, 영향, 조치 방법)을 붙인다.
- 발표 시연: 팀이 일부러 취약하게 만든 테스트 계정 약 2개를 "사용자"로 연결해 전 과정을 보여 준다.
- 발표 자료로 쓸 아키텍처 설명(서비스별 역할, IAM 최소 권한, 보안 설계)을 남긴다.

## 비목표

- 실제 불특정 외부 사용자 모집, 과금, 대규모 확장 (발표에서 말로만 다룬다).
- 점검 규칙을 직접 개발 (Prowler 규칙을 쓴다).
- 점검 대상 웹사이트 외부 스캔 (B안). 후속 확장 후보로만 남긴다.
- 자동 수정(remediation 실행). 조언만 하고 사용자 계정을 변경하지 않는다.

## 안티 목표 (성공해도 실패로 보는 경우)

- 사용자의 액세스 키나 비밀키를 받거나 저장하는 설계.
- 동의 없이 남의 계정을 스캔할 수 있는 구조(confused deputy).
- 시연이 AI 해설 없이 스캐너 출력만 보여 주는 정도에 그치는 것.

## 제약

- 팀 3명, 개발은 사용자 1명 중심. 기간은 약 5주.
- 스캔 대상은 팀 소유 테스트 계정만.
- 비용은 최소화한다. 상시 가동 서버(EC2)보다 서버리스와 필요할 때만 도는 작업을 우선한다.
- 사용자 CLAUDE.md 규칙: 시크릿은 커밋하지 않고, 새 의존성은 필요할 때만 추가한다.

## 정해진 구조 (사용자와 합의한 부분)

- 컨셉: 사용자가 자기 계정을 연결해 빈틈을 확인하는 도구.
- 형태: 서비스 화면을 웹사이트로 제공 (A안).
- AI 활용: 점검 결과 해설과 우선순위 안내.

## 초안 구성 (제 제안, 아직 미확정)

| 역할 | 서비스 |
|------|--------|
| 웹 호스팅 | S3 + CloudFront |
| 로그인 | Cognito |
| API | API Gateway + Lambda |
| 스캔 실행 | CodeBuild 또는 Fargate에서 Prowler 실행 (EventBridge로 스케줄 가능) |
| 결과 저장 | S3(원본 리포트), DynamoDB(항목과 해설) |
| AI 해설 | Lambda에서 Gemini API 호출 (키는 Secrets Manager) |
| 알림 | SNS (위험도 높음일 때) |
| 계정 연결 | 사용자 계정에 읽기 전용 IAM Role 생성(CloudFormation 템플릿 제공), `sts:AssumeRole` + 사용자별 `ExternalId` |

계정 연결 방식이 설계의 핵심이다. 액세스 키는 받지 않고, 사용자가 만든 Role을 임시 자격증명으로만 맡는다. ExternalId로 confused deputy를 막는다. 이 부분은 발표에서 강조할 보안 포인트다.

## 빌더에게 남기는 결정

- 스캔 실행 환경: CodeBuild와 Fargate 중 선택 (비용, 시간 제한, 구현 난이도 비교).
- AI 모델: 사용자 결정으로 Gemini API를 Lambda에서 호출한다(Flash급 우선, Pro는 무료 한도 확인 후). 이 계정에서 Bedrock의 OpenAI GPT-6 Luna는 `AccessDeniedException`(not available for this account)으로 막혀 있음을 콘솔에서 확인했다. Claude는 Anthropic 용도 정보 제출이 필요해 보류했다. API 키는 Secrets Manager 또는 SSM Parameter Store(SecureString)에 두고 코드·레포에 넣지 않는다. 스캔 결과가 Google로 전송되므로 전송 필드를 최소화하고(계정 ID, 리소스 이름 마스킹 검토) 이 점을 발표에서 설명한다. 모델 호출부는 한 함수로 분리해 나중에 Bedrock 모델로 교체할 수 있게 한다.
- 프런트엔드 프레임워크, 리포트 화면 구성.
- 점검 범위: Prowler 전체를 돌릴지, 시연용으로 핵심 항목(S3 공개, Security Group, IAM, 암호화 등)만 돌릴지.
- 팀원별 역할 분담 세부안.

## 계정 구성 (사용자 결정)

- 서비스 계정: 사용자 본인 계정(AWS 계정 ID는 문서에 적지 않고 구현 시 설정값으로 둔다).
- 테스트(고객) 계정 2개: 조원 2명이 각자 자기 AWS 계정을 쓴다. 서비스 계정과 계정이 달라 `AssumeRole` + `ExternalId` 시연이 실제 계정 간 연결로 성립한다.
- 각 조원이 직접 CloudFormation 템플릿을 자기 계정에 실행해 읽기 전용 Role을 만든다. 서비스 쪽은 조원의 액세스 키를 받지 않는다.
- 조원 계정은 본인 동의하에서만 스캔한다. 시연용으로 일부러 취약하게 만든 리소스(공개 S3, 열린 Security Group 등)는 비용·위험 최소로 만들고 시연 후 삭제한다.

## 제 판단 (빌더 점검에서 나온 사소한 항목, 사용자 확인용)

- 프롬프트 인젝션: 스캔 결과의 리소스 이름, 태그, 설명은 신뢰하지 않는 입력으로 다룬다. Gemini에는 필요한 필드만 길이를 제한해 넣고, 출력은 JSON 스키마로 검증한다. 해설 결과가 어떤 실행 동작도 일으키지 않게 한다. 발표에서 보안 설계 포인트로 쓴다.
- 사용자 격리와 보존: DynamoDB 파티션 키에 사용자 ID를 넣고, S3는 `사용자ID/` 접두사로 분리한다. 스캔 결과 삭제 버튼과 S3 수명주기(예: 30일 후 삭제)를 넣는다. Role 연결 해제 기능은 안내 문구 수준으로 한다.
- 읽기 전용 Role 권한: AWS 관리형 정책 `SecurityAudit`과 `ViewOnlyAccess`를 기준으로 한다. 직접 만든 최소 권한 정책은 시간이 남을 때의 개선안으로 두고, 발표에서 "Prowler가 요구하는 권한 범위"를 설명한다.
